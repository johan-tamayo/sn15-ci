## 1. Overview & World Mechanics
- **Pack Path**: `~/sn15-ops/suites/graded30_v2/packs/s14_r22` (`pack_id: p-forge-s14-r22`, `world_id: w-forge-s14-r22`), built by `tools/forge/r22_forge/build_s14_r22.py` from `runs/r22_forge/` + `runs/r22forge1/r22_task_specs_v2.json` (lane r22forge1, FORGE21; a port of `tools/forge/r20_forge/` with race 19's one-at-a-time shopper and its budget / drop / price notices).
- **Corpus Provenance**: all `11,520` released Race-21 open episodes; `2,139` passing order episodes across `24` tasks, `86` passing declines on `1` tasks, `20` tasks with 0 passes.
- **`request_text` = race 21's PUBLIC request text, VERBATIM on 45/45 tasks**: race 21 released none (`query` is null on every episode); field agent `06af481c-5b4dec6e` sends its task input as one JSON chunk in the `BuyerAsk` tool's `Text` argument (a one-element list; the runtime rejects the call - `$.Text: expected string` - and the released episode keeps the argument; the chunk is cut at about 3,200 characters, inside the tool declarations, on most tasks: the request text is its first value and is whole) (`runs/r22_forge/r22_task_inputs.json`, `tools/forge/r22_forge/task_inputs_r22.py`). The spec is forged FROM the text (`tools/forge/r22_forge/specs_r22.py`: requests written as a list are parsed clause by clause, requests written as prose are read by hand).
- **Tool declarations are the live ones** (same echo, `runs/r22_forge/r22_field_tools.json`): names, descriptions, argument schemas and order. Each task carries `params.policy_max_steps` = the live `policy_view.max_steps` of that task (40 x29, 99 x7, 111 x4, 140 x1, 159 x2, 170 x1, 182 x1); `simrace/world_sim.py` passes it as `policy_view.max_steps` (no simulator change was needed for this pack).
- **Truth**: `lita` = shelf listings IN STOCK matching stated + hidden clauses (`clauses_r22.py`: the card's own key decides; an alias key is read only when the own key is absent; when a card shows no attribute for the property, the value in its title) UNION every passing / `not_the_best_option` field cart item on that line MINUS listings a process-complete `request_not_met` order isolates; `reza` = stated-only fits UNION lita; one answer slot per event bitmask. Listings no field agent opened (`1,930` of `4,576`) carry no attributes: `Examine` shows them with empty `facts` and they are never acceptable by clause.
- **Catalog**: all `4,576` listings seen in the episodes (`2,646` full cards, `615` with a seller note in `remarks_section`) on 31 shelves (AV Receivers & Amplifiers, Antennas and Coax Cables, Area Rugs, Blank Discs, Blankets & Throws, Canned Fish & Seafood, Computer Monitors, Denim Jackets, Dinnerware Sets, Dishwasher Detergent, Dog Wet Food, Door Handles and Locks, Formal, Hardware, Home Soundbars, Speakers & Subwoofers, Karaoke Systems, Lighting Installation & Accessories, Microwaves, Natural Sweeteners, Pasta and Noodles, Pepper, Pillow Cases & Bolster Cases, Portable Monitors, Power Supply Units, Protein Powders, Streaming Media Players, Sunscreen, Sunscreen & Aftersun, Wardrobe Organisers, Wardrobes, Watches); `2` listings are out of stock from the start (`ready` false; every request says a sold-out listing is no good).
- **Task mix**: 1L `20` / 2L `5` / 3L `15` / 4L `1` / 5L `4` / 6L `0`; hidden needs on `35/45` tasks (62 needs; 1 task(s) carry one more need no field agent ever got revealed: `t-6937b3f101`), reply-by-reference on `14`, reference chains on `22` (11 stated in the request, 15 revealed; 1 to 6 pages), store notices on `14` (budget 11, drop 5, stock 1), lowest-price tasks `17`, decline-correct tasks `1`, did-not-understand tasks `21`, device compatibility on `16` tasks (41 pairs), conditional clauses on `6`, a per-line cap on `2`.
- **7 Race-21 Tools (`tools.json`)**: `Examine` (`TargetItem`: the full card; an id the store does not hold -> `{}`), `ListingsSearch` (`SearchWay` phrase = keyword search over `FindTerms`, criteria = a filter listing by `Aisle` / `ProductMake` / `LimitLimit`; 7 rows a call from `SkipRows` 0..56; `page_next_token` = the next `SkipRows` while more rows remain; `found_number` of a keyword search stops at 200), `SummaryBag` (the order list + `owed`), `StashToCart` (`Stuff`: a list of `{Ref, N}`, N 1..4, at most 10 entries - the list REPLACES the whole order list and the reply is the new order list), `SummaryBalance` (`{duzova: {points_burned, unspent_count}}`: the message meter), `BuyerAsk` (2 replies, then `{"error": "budget_exceeded"}`), `OrderWrapUp` (`WayChoice` commit: an empty order list -> `{"issue_text": "EMPTY"}`; cancel: a decline). There is NO batch view in race 21: every page costs one `Examine` step.
- **Split view**: a `ListingsSearch` row is `brand, description, item_id_code, label_line, merchant, product_shelf, ready, unit_list_price`; `facts` and `remarks_section` (the seller's blurb, where the pointer sentences sit) appear only on `Examine`.
- **Search has two styles that do not mix**: `phrase` reads `FindTerms` only (`Aisle`, `ProductMake` and `LimitLimit` are ignored: a keyword search runs over the whole store, every word must be in the listing's title / producer / seller / shelf / attribute values, the matches come in ascending listing id); `criteria` reads `Aisle` (the shelf's name as the store writes it, case ignored; any other name lists nothing), `ProductMake` (the listing's brand) and `LimitLimit` (the highest unit price let through - it is NOT a page size) and ignores `FindTerms`; a criteria search with neither `Aisle` nor `ProductMake` answers `{}`. The description (where `Model ref. ROK 1840.`, `Goes with every ROK 18xx model.` and `Compatible part series: RO3.` stand) is not searched.
- **Compatibility is strict and said on the listing** (`Whatever <devices> you choose, the <accessories> must be compatible with it.`): a dust plug / wall charger / power adaptor must SAY it goes with the phone's family (`description` opens with `Goes with every ROK 18xx model.` for a phone whose `description` opens with `Model ref. ROK 1840.`); a wireless charger / cable / earbud case works with an office headset when its part series (title `... (part RO3-4528)`) is the headset's (`description`: `Model ref. BEZ-4410. Compatible part series: RO3.`).
- **Reference chains**: a reference names a page by seller, shelf and attributes (`only whatever you get to from the page of the wireless chargers from Shilenkako that comes with connection type wireless, color black and power source rechargeable, following every listing it names`); decoy pages of the same seller sit beside it (`A version with ... exists elsewhere.`). The pointer sentence is in `remarks_section` (`For plug type, look to the Wall Chargers product from Lukatador, listed with input voltage 100-240 v and power 25w.`). Relations: `only` (that value), `a good fit with` (the partner the terminal page's pairing rule names: `The store's plug type rule: 2 pin goes with 3 pin, cn goes with us, ...`), `anything but` (any other value).
- **Store Notices**: three triggers - `first_add` (the first `StashToCart` that leaves a line in the order list), `after_reveal` (the first need the shopper reveals), `finish` (the first `OrderWrapUp`) - after_reveal 3, finish 10, first_add 4; kinds `budget` (the sentence names the new whole-order cap in pence; the wording does not tell the direction), `drop` (a requirement the shopper lets go: the lists relax), `price` (the FIRST listing of the order list is repriced to `old * pct // 100`; pct -). A notice with an echo rides on the NEXT call as `{"tezazu": [<sentence>...], "vaza": <obs>}` (`vaza` of a `BuyerAsk` is the bare reply string); 0 event(s) are SILENT (no echo: the change shows only in the refusal of a close or on a re-read). Everything not yet fired fires at the first close, which is refused once (`{"observation": {"accepted_flag": true}, "refusal": [...]}`: `accepted_flag: true` INSIDE `observation` with the sentences beside it means NOTHING was ordered); a price event is void on a `cancel` close or an empty order list; a close right after a refused close goes through.
- **Persona**: 12 reveal frames of a home cook who follows the village cricket (`tools/forge/r22_forge/r22_defs_frames.py`), 10 no-preference + 10 did-not-understand replies and 10 ONE-AT-A-TIME replies (`runs/r22_forge/r22_reply_pools.json`); 2 messages.
- **One at a time**: the shopper answers a message about ONE of its subjects (its hidden needs + decoy properties, each a property of one item) and pushes a message it reads as several questions back with a one-at-a-time line. The decoy subjects of each task are read off the field's one-at-a-time replies (`subjects_r22.py`; subjects per task 2 x6, 3 x14, 4 x25; the rule `two or more subjects named <=> one at a time` reads 92.3% of the parsed field questions right); the share told / pushed back comes from the message's cell of the fitted table (below); any other question gets the task's ONE off-need pool (`dnu_default` on 21 tasks, no-preference on the others).
- **Process rules**: every hidden need revealed via `BuyerAsk`; every page of a reference chain opened via `Examine` (`answer.refs` stated chains; `answer.need_refs` chains of needs revealed by reference, orders only); EVERY ORDERED LISTING opened at some point (`process_rules: ["ordered_listing_opened"]`). A decline is never process-missed.
- **Grading**: `not the best option` = acceptable but above the lowest total (on lowest-price tasks; after a price move the lowest total is the cheapest acceptable basket LEFT); an order that violates a revealed need, or that a price move or a new cap pushed over the cap, is `request not met`.
- **Not reproduced**: a call the runtime rejects before the world (`invalid_arguments`) does not spend one of the task's steps in the simulator's step meter (live: every call counts toward `max_steps`). After the step budget the simulator answers `budget_exceeded` and leaves the session open.
- **No acceptable basket derivable** (0 field passes; the clauses + field carts leave a line empty; a decline is still graded request_not_met as in the field): `t-22e76fd3ed`.
- **Never-revealed need** (every order is process-missed, as in the field): `t-6937b3f101`.
