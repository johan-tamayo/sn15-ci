# Race-21 Forged Field Suite (`s14_r21`, 45 Open Tasks, `w-forge-s14-r21`)

## 1. Overview & World Mechanics
- **Pack Path**: `~/sn15-ops/suites/graded30_v2/packs/s14_r21` (`pack_id: p-forge-s14-r21`, `world_id: w-forge-s14-r21`), built by `tools/forge/r21_forge/build_s14_r21.py` from `runs/r21_forge/` + `runs/r21forge1/r21_task_specs_v2.json` (lane r21forge1, FORGE21; a port of `tools/forge/r20_forge/` with race 19's one-at-a-time shopper and its budget / drop / price notices).
- **Corpus Provenance**: all `11,835` released Race-21 open episodes; `2,994` passing order episodes across `30` tasks, `33` passing declines on `1` tasks, `14` tasks with 0 passes.
- **`request_text` = race 21's PUBLIC request text, VERBATIM on 45/45 tasks**: race 21 released none (`query` is null on every episode); field agent `06af481c-5b4dec6e` sends its task input as one JSON chunk in the `BuyerAsk` tool's `Text` argument (a one-element list; the runtime rejects the call - `$.Text: expected string` - and the released episode keeps the argument; the chunk is cut at about 3,200 characters, inside the tool declarations, on most tasks: the request text is its first value and is whole) (`runs/r21_forge/r21_task_inputs.json`, `tools/forge/r21_forge/task_inputs_r21.py`). The spec is forged FROM the text (`tools/forge/r21_forge/specs_r21.py`: requests written as a list are parsed clause by clause, requests written as prose are read by hand).
- **Tool declarations are the live ones** (same echo, `runs/r21_forge/r21_field_tools.json`): names, descriptions, argument schemas and order. Each task carries `params.policy_max_steps` = the live `policy_view.max_steps` of that task (35 x35, 74 x1, 85 x1, 95 x2, 99 x1, 109 x4, 120 x1); `simrace/world_sim.py` passes it as `policy_view.max_steps` (no simulator change was needed for this pack).
- **Truth**: `lita` = shelf listings IN STOCK matching stated + hidden clauses (`clauses_r21.py`: the card's own key decides; an alias key is read only when the own key is absent; when a card shows no attribute for the property, the value in its title) UNION every passing / `not_the_best_option` field cart item on that line MINUS listings a process-complete `request_not_met` order isolates; `reza` = stated-only fits UNION lita; one answer slot per event bitmask. Listings no field agent opened (`2,771` of `5,328`) carry no attributes: `Examine` shows them with empty `facts` and they are never acceptable by clause.
- **Catalog**: all `5,328` listings seen in the episodes (`2,557` full cards, `589` with a seller note in `remarks_section`) on 14 shelves (Ceiling Lights, Desk Fans, Dust Plugs, Earbud and Headphone Cases, Feature Phones, Grains, Light Fixtures, Milk Tea, Office Headsets, Power Adaptors & Chargers, Tops & Tees, USB and Lightning Cables, Wall Chargers, Wireless Chargers); `8` listings are out of stock from the start (`ready` false; every request says a sold-out listing is no good).
- **Task mix**: 1L `24` / 2L `6` / 3L `9` / 4L `6` / 5L `0` / 6L `0`; hidden needs on `35/45` tasks (40 needs; 1 task(s) carry one more need no field agent ever got revealed: `t-d27c1d1b54`), reply-by-reference on `3`, reference chains on `11` (10 stated in the request, 3 revealed; 1 to 5 pages), store notices on `14` (budget 13, drop 2, price 2), lowest-price tasks `30`, decline-correct tasks `1`, did-not-understand tasks `13`, device compatibility on `10` tasks (16 pairs), conditional clauses on `8`, a per-line cap on `3`.
- **7 Race-21 Tools (`tools.json`)**: `Examine` (`TargetItem`: the full card; an id the store does not hold -> `{}`), `ListingsSearch` (`SearchWay` phrase = keyword search over `FindTerms`, criteria = a filter listing by `Aisle` / `ProductMake` / `LimitLimit`; 7 rows a call from `SkipRows` 0..56; `page_next_token` = the next `SkipRows` while more rows remain; `found_number` of a keyword search stops at 200), `SummaryBag` (the order list + `owed`), `StashToCart` (`Stuff`: a list of `{Ref, N}`, N 1..4, at most 10 entries - the list REPLACES the whole order list and the reply is the new order list), `SummaryBalance` (`{duzova: {points_burned, unspent_count}}`: the message meter), `BuyerAsk` (2 replies, then `{"error": "budget_exceeded"}`), `OrderWrapUp` (`WayChoice` commit: an empty order list -> `{"issue_text": "EMPTY"}`; cancel: a decline). There is NO batch view in race 21: every page costs one `Examine` step.
- **Split view**: a `ListingsSearch` row is `brand, description, item_id_code, label_line, merchant, product_shelf, ready, unit_list_price`; `facts` and `remarks_section` (the seller's blurb, where the pointer sentences sit) appear only on `Examine`.
- **Search has two styles that do not mix**: `phrase` reads `FindTerms` only (`Aisle`, `ProductMake` and `LimitLimit` are ignored: a keyword search runs over the whole store, every word must be in the listing's title / producer / seller / shelf / attribute values, the matches come in ascending listing id); `criteria` reads `Aisle` (the shelf's name as the store writes it, case ignored; any other name lists nothing), `ProductMake` (the listing's brand) and `LimitLimit` (the highest unit price let through - it is NOT a page size) and ignores `FindTerms`; a criteria search with neither `Aisle` nor `ProductMake` answers `{}`. The description (where `Model ref. ROK 1840.`, `Goes with every ROK 18xx model.` and `Compatible part series: RO3.` stand) is not searched.
- **Compatibility is strict and said on the listing** (`Whatever <devices> you choose, the <accessories> must be compatible with it.`): a dust plug / wall charger / power adaptor must SAY it goes with the phone's family (`description` opens with `Goes with every ROK 18xx model.` for a phone whose `description` opens with `Model ref. ROK 1840.`); a wireless charger / cable / earbud case works with an office headset when its part series (title `... (part RO3-4528)`) is the headset's (`description`: `Model ref. BEZ-4410. Compatible part series: RO3.`).
- **Reference chains**: a reference names a page by seller, shelf and attributes (`only whatever you get to from the page of the wireless chargers from Shilenkako that comes with connection type wireless, color black and power source rechargeable, following every listing it names`); decoy pages of the same seller sit beside it (`A version with ... exists elsewhere.`). The pointer sentence is in `remarks_section` (`For plug type, look to the Wall Chargers product from Lukatador, listed with input voltage 100-240 v and power 25w.`). Relations: `only` (that value), `a good fit with` (the partner the terminal page's pairing rule names: `The store's plug type rule: 2 pin goes with 3 pin, cn goes with us, ...`), `anything but` (any other value).
- **Store Notices**: three triggers - `first_add` (the first `StashToCart` that leaves a line in the order list), `after_reveal` (the first need the shopper reveals), `finish` (the first `OrderWrapUp`) - after_reveal 10, finish 7; kinds `budget` (the sentence names the new whole-order cap in pence; the wording does not tell the direction), `drop` (a requirement the shopper lets go: the lists relax), `price` (the FIRST listing of the order list is repriced to `old * pct // 100`; pct 75, 141). A notice with an echo rides on the NEXT call as `{"tezazu": [<sentence>...], "vaza": <obs>}` (`vaza` of a `BuyerAsk` is the bare reply string); 1 event(s) are SILENT (no echo: the change shows only in the refusal of a close or on a re-read). Everything not yet fired fires at the first close, which is refused once (`{"observation": {"accepted_flag": true}, "refusal": [...]}`: `accepted_flag: true` INSIDE `observation` with the sentences beside it means NOTHING was ordered); a price event is void on a `cancel` close or an empty order list; a close right after a refused close goes through.
- **Persona**: 12 reveal frames of a home cook who follows the village cricket (`tools/forge/r21_forge/r21_defs_frames.py`), 10 no-preference + 10 did-not-understand replies and 10 ONE-AT-A-TIME replies (`runs/r21_forge/r21_reply_pools.json`); 2 messages.
- **One at a time**: the shopper answers a message about ONE of its subjects (its hidden needs + decoy properties, each a property of one item) and pushes a message it reads as several questions back with a one-at-a-time line. The decoy subjects of each task are read off the field's one-at-a-time replies (`subjects_r21.py`; subjects per task 2 x2, 3 x14, 4 x29; the rule `two or more subjects named <=> one at a time` reads 90.7% of the parsed field questions right); the share told / pushed back comes from the message's cell of the fitted table (below); any other question gets the task's ONE off-need pool (`dnu_default` on 13 tasks, no-preference on the others).
- **Process rules**: every hidden need revealed via `BuyerAsk`; every page of a reference chain opened via `Examine` (`answer.refs` stated chains; `answer.need_refs` chains of needs revealed by reference, orders only); EVERY ORDERED LISTING opened at some point (`process_rules: ["ordered_listing_opened"]`). A decline is never process-missed.
- **Grading**: `not the best option` = acceptable but above the lowest total (on lowest-price tasks; after a price move the lowest total is the cheapest acceptable basket LEFT); an order that violates a revealed need, or that a price move or a new cap pushed over the cap, is `request not met`.
- **Not reproduced**: a call the runtime rejects before the world (`invalid_arguments`) does not spend one of the task's steps in the simulator's step meter (live: every call counts toward `max_steps`). After the step budget the simulator answers `budget_exceeded` and leaves the session open.
- **No acceptable basket derivable** (0 field passes; the clauses + field carts leave a line empty; a decline is still graded request_not_met as in the field): `t-45c76c05d9`, `t-857c3a2ad0`.
- **Never-revealed need** (every order is process-missed, as in the field): `t-d27c1d1b54`.
